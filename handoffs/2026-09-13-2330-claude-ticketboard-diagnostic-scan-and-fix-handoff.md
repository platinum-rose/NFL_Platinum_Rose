### 3.4 MAJOR FINDING — the spec's own storage architecture section is wrong
Spec Section 4 claims "seven primary isolated state stores" in localStorage and gives a table of key names (`CHECKED_LEGS_KEY` → `sunday_checked_legs_week_{w}`, `BURNT_KEY` → `sunday_manual_burns_week_{w}`, `ORDER_KEY` → `sunday_cards_order_week_{w}`, etc.).

The actual code (`scripts/generate-live-tracker.mjs`, lines ~3543-3563) defines **20 separate localStorage keys**, and several of the spec's claimed key strings do not match the real ones:

| Spec claims | Spec's key string | Actual code | Actual key string |
|---|---|---|---|
| `CHECKED_LEGS_KEY` | `sunday_checked_legs_week_{w}` | *(no such dedicated key exists)* | `checkedState` is read from `STORAGE_KEY` = `sunday_tracker_state_week_${week}` — a **shared/consolidated blob**, not its own key |
| `BURNT_KEY` | `sunday_manual_burns_week_{w}` | `BURNS_KEY` | `sunday_burns_week_${week}` (different string) |
| `CASHED_KEY` | `sunday_manual_cashed_week_{w}` | `CASHED_KEY` | `sunday_cashed_state_week_${week}` (different string) |
| `ORDER_KEY` | `sunday_cards_order_week_{w}` (plural "cards") | `ORDER_KEY` | `sunday_card_order_week_${week}` (singular "card") |

`BURNT_LEGS_KEY`, `HIDE_FULFILLED_LEGS_KEY`, `SPLITS_KEY`, and `COLLAPSED_KEY` do match between spec and code.

**Why this matters:** anyone (agent or human) who patches code by trusting the spec's key-name table instead of the real file will silently target the wrong localStorage key, which either does nothing or introduces a new corruption. The spec is not a reliable map of the current codebase and needs to be corrected or discarded in favor of reading the real file directly.

### 3.5 HIGH-VALUE HYPOTHESIS NOT YET RULED OUT — dual-origin localStorage split
This wasn't in Antigravity's spec at all, and is worth checking **first** in the fresh session because it's cheap to verify and would fully explain "state reverted 10 versions back" without any JS bug at all:

- `public/live-tracker-sunday.html` and `docs/tracked-wagers/live-tracker-sunday.html` are two **separately generated, byte-different-path copies** of the same HTML, written by the same `generate-live-tracker.mjs` run.
- `docs/` is deployed via GitHub Pages (`.github/workflows/*.yml` has a "Deploy to GitHub Pages" job that publishes the `docs/` folder). `public/` is presumably served by whatever local/dev/production web server serves the main NFL Dashboard app — a **different origin** than GitHub Pages.
- Browser `localStorage` is scoped per-origin (and often per-full-path for `file://` URLs). If Andy was clicking hits/burns/splits all day on one URL (say, the local dev server's `public/` copy) and at some point today's Antigravity changes caused him to reload or get redirected to the **other** copy (the GitHub Pages `docs/` URL, or vice versa), **every single localStorage key would read back empty** on the new origin — recreating exactly the symptom described ("reverted 10 versions back," scoreboard badges cleared).
- **Action for fresh session:** ask Andy which exact URL(s) he was actually using throughout the day (local dev URL vs. the GitHub Pages URL), check browser history/tabs if possible, and confirm whether a link/redirect embedded anywhere in the app (e.g. a "Refresh" or "Open Tracker" button) points to a different origin than what he'd been using. If confirmed, the fix might be as simple as picking one canonical URL and making every internal link point to it — no JS bug-hunting required at all.

### 3.6 Ledger and data-pipeline itself: verified clean, not the problem
Confirmed earlier this session (separate from this scan): the master wager ledger (`data/official-picks/user-placed-wagers-2026.json`), the sync script (`scripts/sync-placed-wagers-to-bankroll.mjs`), and `scripts/generate-live-tracker.mjs`'s *ingestion* logic are all working correctly and match Andy's actual placed tickets — 24 wagers currently, all correctly propagated to `public/user-placed-wagers-2026.json` and Supabase `user_bankroll_bets`. **The "which teams covered / totals hit / players hit" data problem is a client-side (browser) state and/or rendering-logic problem, not a data-pipeline or ledger problem.** Don't waste time re-auditing the ledger itself — start from the tracker's client-side JS and localStorage architecture.

### 3.7 Leg-key stability: checked, not the cause
Considered and ruled out: leg identity keys (`leg_${bet.id}_${legIndex+1}`, generated at line ~874) are scoped per-ticket-id and per-leg-index-within-that-ticket, so adding new tickets elsewhere in the wager array (as happened twice tonight when the 3 new SNF DraftKings combos were logged) does **not** shift or invalidate existing tickets' leg keys. This is not the cause of lost history.
