# Platinum Rose AI Official Picks Spec - 2026 NFL

## Purpose

Platinum Rose AI is a tracked paper expert, not an autonomous betting engine. It can propose futures and weekly bets, but a play becomes an official tracked paper bet only after human verification.

The goal is to grade Platinum Rose AI against Andy and other experts across:

- futures portfolio results
- weekly sides, totals, moneyline dogs, props, teasers, and parlays
- unit profit/loss, win-loss-push, ROI, and closing-line value where available

## Identity

- Expert id: `platinum_rose_ai`
- Display name: `Platinum Rose AI`
- Mode: `paper_tracked_human_verified`
- Season: `2026`

## Bankrolls And Units

| Portfolio | Bankroll | Unit | Allowed sizes |
|---|---:|---:|---|
| Futures | $500 | $20 | 0.25u, 0.5u, 1u, 2u |
| In-season weekly | $1000 | $10 | 0.25u, 0.5u, 1u, 2u |

Recommended stake-tier mapping:

| Stake tier | Units | Use case |
|---|---:|---|
| `speculative` | 0.25u | longshot, option ticket, thin market, early watchlist conversion |
| `small` | 0.5u | plus-odds value, hedge/coverage, uncertain but price-sensitive |
| `standard` | 1u | normal official play with adequate edge and evidence |
| `core` | 2u | highest-conviction, broadly supported edge; rarely used |

## Futures Cutoff

User-specified cutoff: **September 9, 2026 at 12:00 PM PST**.

Canonical tracking timestamp:

- Local: `2026-09-09T12:00:00-07:00` in `America/Los_Angeles`
- UTC: `2026-09-09T19:00:00Z`

Note: Los Angeles is on daylight time in September, so the canonical offset is `-07:00`. The original user label is preserved for audit.

Before the cutoff, Platinum Rose AI may propose futures for review. It should account for preseason price movement, late-opening derivative markets, and the possibility that in-season futures may offer better entries after performance or injury-driven price swings.

After the cutoff, futures can still be tracked as in-season futures when the rationale depends on new information or changed prices. They should be clearly tagged as in-season futures, not part of the initial preseason futures card.

## Official Pick Lifecycle

1. `proposal`
   Platinum Rose AI identifies a candidate and explains the market case, football case, evidence, disconfirming factor, price threshold, and suggested unit size.

2. `human_verified`
   Andy verifies the price/source and approves the candidate for paper tracking.

3. `official_paper`
   The play is locked with timestamped odds, source, stake units, bankroll context, and rationale. Official records should not be retro-edited except to correct clerical errors with an audit note.

4. `graded`
   Result, net units, payout, and grading note are recorded.

5. `void` or `superseded`
   Used for cancelled markets, bad lines, data errors, or explicitly replaced proposals.

## Local Ledger Workflow

The local ledger is the approval-first paper record for Platinum Rose AI:

- Ledger file: `data/official-picks/platinum-rose-ai-2026.json`
- CLI entrypoint: `node scripts/official-pick-ledger.js`
- Project shortcut: `npm run official:picks -- <command>`

Initialize or inspect the ledger:

```powershell
npm run official:picks:init
npm run official:picks:summary
npm run official:picks -- list
npm run official:picks:report
```

The report command writes local review artifacts to `.nfl/official-picks/`:

- `platinum_rose_ai_2026-ledger.html`
- `platinum_rose_ai_2026-ledger.md`
- `platinum_rose_ai_candidate_inbox.html`
- `platinum_rose_ai_candidate_inbox.md`

These reports are read-only artifacts derived from the JSON ledger. They do not publish to Supabase or create official picks.

Run the local interactive inbox when Andy wants approve/reject buttons:

```powershell
npm run official:picks:serve
```

Then open `http://127.0.0.1:8787/`. This page reads the active draft folder, validates each draft, and sends approve/reject actions back through the same local ledger commands. Approve locks a valid draft as an official paper pick; reject archives a bad draft. It still does not place a real bet or write to Supabase.

One-click Windows launcher:

- Double-click `Launch Platinum Rose Inbox.cmd` from the project root.
- Leave the server window open while approving or rejecting drafts.
- Close that window when finished.

The post-approval scorecard is regenerated by `official:picks:report` and lives at `.nfl/official-picks/platinum_rose_ai_2026-ledger.html`.

## Candidate Inbox Management

Draft proposals live in three local folders:

- `data/official-picks/proposals/active/`
- `data/official-picks/proposals/promoted/`
- `data/official-picks/proposals/rejected/`

Review active drafts:

```powershell
npm run official:picks:inbox
```

Approve a valid draft as an official tracked paper pick:

```powershell
npm run official:picks:approve -- --file data/official-picks/proposals/active/<draft>.json
```

Approval validates the draft, records it in the ledger, marks it human-verified, locks it as `official_paper`, and archives the draft JSON under `proposals/promoted/`. This is still fake/paper tracking only; it does not place a real bet and does not write to Supabase.

Reject a bad draft:

```powershell
npm run official:picks:reject -- --file data/official-picks/proposals/active/<draft>.json --reason "price stale or thesis unsupported"
```

Rejection archives the draft JSON under `proposals/rejected/` with the reason preserved in `inbox_state`.

Optional lower-level flow: promote a draft into the ledger as a `proposal` without locking it:

```powershell
npm run official:picks:promote -- --file data/official-picks/proposals/active/<draft>.json
```

Promotion does not make a pick official. It records the candidate in the ledger as `proposal` / `proposed`, then archives the draft JSON under `proposals/promoted/`.

## Futures Agent Candidate Export

Offline portfolio synthesis can export final validated candidates into the Platinum Rose proposal inbox without touching the official ledger:

```powershell
node agents/portfolio-synthesize.js --dossier .nfl/portfolio/dossier-2026-07-22.json --no-persist --proposal-out-dir data/official-picks/proposals/active
```

The export creates one draft JSON file per final candidate plus a `candidate-inbox-*.json` and `candidate-inbox-*.md` manifest in the same directory. These are proposal drafts only. They still need review, optional editing, `official:picks:validate`, and explicit promotion with `official:picks:promote` before they enter the ledger.

For offline plumbing QA, use the mocked corpus runner:

```powershell
npm run official:proposals:export-test
```

Create a draft proposal template:

```powershell
npm run official:picks:new -- --scope futures --team Bills --market-type wins --selection "Bills Over 11.5"
npm run official:picks:new -- --scope weekly --team Packers --market-type spread --selection "Packers -2.5"
```

Draft templates are written under `data/official-picks/proposals/active/` unless `--out <path>` is provided. They are not proposals yet and do not alter the ledger.

Validate a draft before recording it:

```powershell
npm run official:picks:validate -- --file data/official-picks/proposals/<draft>.json
npm run official:picks:validate -- --file data/official-picks/proposals/<draft>.json --strict
```

Validation reports whether the draft is proposal-ready, whether it is lock-ready, and which fields still need human/source work. `--strict` returns a failing exit code when the candidate still has warnings.

Record a proposal from a JSON candidate file:

```powershell
npm run official:picks -- propose --file data/official-picks/examples/platinum-rose-ai-proposal.example.json
```

The proposal command does not create an official pick. It stores the candidate as `proposal` / `proposed`.

After Andy verifies the price/source, mark it human-verified:

```powershell
npm run official:picks -- verify --pick-id <pick_id> --source-ref "<verified source>" --observed-at <iso_timestamp>
npm run official:picks:validate -- --pick-id <pick_id>
```

Lock a verified pick as official paper tracking:

```powershell
npm run official:picks -- lock --pick-id <pick_id>
```

The lock command refuses to proceed unless the play has human verification, timestamped odds, source evidence, confidence, threshold/edge context, rationale, a disconfirming factor, and evidence ids. Exacta and Super Bowl matchup markets remain monitor-only and cannot be locked while the current BetOnline price-shopping hold is active.

Grade a resolved official paper pick:

```powershell
npm run official:picks -- grade --pick-id <pick_id> --result won
npm run official:picks -- grade --pick-id <pick_id> --result lost
npm run official:picks -- grade --pick-id <pick_id> --result push
```

When possible, grading infers `net_units` from American odds and stake size. Use `--net-units <n>` when the market has a custom payout, partial result, parlay, teaser, or settlement nuance.

This local workflow does not write to Supabase. A later seed/sync command can be added after explicit approval to publish official paper picks into the `official_picks` tables.

## Official Pick Requirements

An official Platinum Rose AI play requires:

- placeable book or source
- timestamped odds
- market, selection, price, line when applicable
- stake units and bankroll context
- confidence grade
- minimum edge threshold or bet threshold
- written rationale
- separate market view and football view
- disconfirming factor
- evidence ids that point back to dossier fields or source records
- human verification before official tracking

## Market Holds

Exacta and Super Bowl matchup plays are monitor-only until a secondary BetOnline market appears for price shopping against BetUS or another placeable book. Single-book exacta rows can support scenario planning, but should not become official tracked plays until the price-shopping condition is satisfied.

## Data Fields The AI Should Ask About

For every futures or weekly candidate, Platinum Rose AI should answer:

- Is the price placeable, fresh, and better than the threshold?
- Is the market edge mathematical, thesis-based, stale-price, hedge-driven, or longshot convexity?
- Does DVOA, EPA, EPA/dropback, success rate, CPOE, explosive rate, pressure/sack data, schedule context, injuries, roster churn, or coaching tendency support the play?
- What would prove the play wrong?
- Is this a current play, a wait, a pair, or a pass?
- Does this duplicate existing exposure, hedge an anchor team, or create useful later option value?
- Is the stake size appropriate for bankroll, variance, market liquidity, and evidence quality?
